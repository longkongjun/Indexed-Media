# 使用持久任务与文件操作日志

> 日期：2026-07-17
> 状态：accepted

## 背景

MediaFlow 需要在家庭 NAS 上持续处理大文件，并在 Core 重启、重复发现、单文件失败和部分成功后恢复。SQLite 事务不能覆盖已经发生的文件系统变化，跨文件系统移动也不存在可依赖的统一事务。

## 决定

每个发现文件使用一个持久 `ProcessingTask` 表达完整处理时间线，扫描批次只聚合文件任务。任务使用阶段、状态、租约和幂等检查点协调领域模块。

所有文件与 NFO 变化必须先创建持久 `OrganizationPlan` 和具有稳定 ID 的 `FileOperationJournal`。恢复时核对数据库检查点与实际文件状态；已验证步骤不得重复执行，无法可靠判断时进入人工处理。

内部状态和 outbox 事件在同一 SQLite 事务中提交，消费者按稳定事件 ID 支持至少一次交付。

## 后果

正面后果：

- 重复发现可以复用原任务，不产生重复文件副作用。
- 单文件失败不会中止扫描批次。
- 文件操作成功而 NFO 失败时可以精确重试未完成步骤。
- 任务时间线、审计和 Web 恢复动作具有同一证据来源。

代价与限制：

- Worker、journal 和恢复核对需要显式状态机和故障注入测试。
- 不承诺跨文件或跨文件系统的整体原子性。
- 状态不明确时需要管理员介入，不能为了自动化盲目重放。

## 未采用方案

- 每个阶段独立创建任务：重试灵活，但用户难以追踪一个文件的完整因果链。
- 整个扫描批次使用一个大型任务：单文件隔离、恢复和并发控制较差。
- 只依赖数据库事务后补偿文件系统：进程崩溃窗口无法可靠解释。

# 使用类型化内置连接器能力

> 日期：2026-07-17
> 状态：accepted

## 背景

TMDB、Jellyfin、下载器、通知渠道和本地模型的能力、失败方式与授权边界不同。把它们压入单一通用连接器接口会隐藏差异，并可能让 Jellyfin 因“媒体服务器连接器”身份意外获得媒体库映射、扫描或任务状态能力。

MVP 只需要 TMDB 元数据能力和 Jellyfin 独立健康能力，M4 才增加下载来源、通知和一个内置本地模型适配器。

## 决定

Core 按能力类型定义编译期端口，例如 `MetadataProvider`、`ServiceHealthProvider`、`IdentificationEnhancer`、`DownloadSource` 和 `NotificationSink`。内置适配器只声明实际支持的能力、配置版本、超时、重试和健康状态。

MVP 的 Jellyfin 适配器只实现连接测试、健康状态和首页地址。它不实现媒体库列表、映射、扫描、可见性验证或媒体级跳转，也不能改变本地处理任务状态。

M4 的本地模型只作为可选 `IdentificationEnhancer`；关闭、超时或失败时回到确定性识别路径。MVP 不提供动态插件、外部 provider SDK 或任意脚本运行时。

## 后果

正面后果：

- 领域模块依赖明确能力，不依赖具体外部产品。
- 连接器最小权限和故障隔离可以按能力验证。
- Jellyfin 与本地整理任务的解耦成为结构约束，而不只是界面约定。
- 后续本地模型可以关闭和降级，不成为基础闭环依赖。

代价与限制：

- 不同能力需要各自端口和 fixture，接口数量多于单一通用连接器。
- 新外部系统只有在能力明确后才能接入，不能通过任意动作快速绕过边界。
- 第三方插件生态继续延后，多个稳定实现出现前不提炼公共协议。

## 未采用方案

- 单一通用连接器动作/事件接口：容易形成最低公分母和权限膨胀。
- 各领域直接依赖具体 HTTP 客户端：替换、降级和测试隔离较差。
- 现在建设动态插件运行时：没有 MVP 需求，也缺少稳定能力与安全模型。

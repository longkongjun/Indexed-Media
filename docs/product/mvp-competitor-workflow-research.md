# MVP 竞品工作流研究

> 日期：2026-07-14
> 状态：已验收
> 适用范围：M1 MVP 需求与体验定义

## 1. 研究目标

本研究比较 MoviePilot、Infuse、Jellyfin、Emby 和 Plex 在个人 NAS 影视资源生命周期中的真实职责，为 MediaFlow MVP 的用户、范围、流程和验收场景提供输入。

研究以端到端工作流为主，不按功能数量评价产品，也不把不同角色的产品强行放在同一维度竞争。重点观察：

```text
资源进入
  -> 文件发现
  -> 识别与元数据
  -> 人工纠错
  -> 文件整理
  -> 媒体服务器刷新
  -> 浏览与外部播放
```

研究只使用截至 2026-07-14 可访问的官方文档。结论描述文档公开呈现的行为，不代表完整产品审计或真实环境可用性测试。

## 2. MediaFlow 既有边界

本研究不重新决定已经确认的产品边界：

- MediaFlow 是本地优先、自托管的家庭 NAS 数字资源中枢。
- MediaFlow 负责发现、识别、整理、建立媒体记录和向下游分发。
- MediaFlow 不负责播放、转码、字幕渲染或播放进度主数据。
- MediaFlow 不内置私有站点 Cookie、资源聚合搜索或站点适配。
- MediaFlow 不依赖 n8n、Dify 或必需的云端控制面。

本研究只回答：在这些边界内，MediaFlow 应如何形成比现有多产品拼接更清晰、更安全的资源交接流程。

## 3. 产品角色

### 3.1 工作流角色

| 产品 | 工作流中的主要角色 | 对 MediaFlow 的参考价值 | 明确不照搬 |
| --- | --- | --- | --- |
| MoviePilot | 从搜索、订阅或下载完成进入识别、整理和媒体服务器刷新的自动化编排器 | 下载器与目录监控、后台任务、整理历史、重新整理和下游刷新 | 私有站点、Cookie、资源聚合搜索及依赖站点生态的能力 |
| Jellyfin | 扫描规范化媒体目录、匹配元数据并向客户端提供媒体库和播放服务 | 文件命名、目录结构、NFO、provider ID 和本地优先部署 | 播放、转码、用户播放状态和客户端生态 |
| Emby | 管理媒体库、元数据和多客户端消费 | 可视化资源库配置、Identify、字段级元数据管理和刷新策略 | 播放、转码、云账号或客户端商业能力 |
| Plex | 扫描、匹配、元数据管理和多客户端消费 | Scan 与 Refresh 的语义区分、Fix Match 和成熟媒体组织约定 | 播放、转码、云端账号和在线内容生态 |
| Infuse | 消费文件共享或媒体服务器中的目录、元数据和播放状态 | 媒体墙、版本选择、快速更新和外部消费体验 | 播放器、播放进度主数据和 Apple 平台专属能力 |

这些产品不是五个同类替代品。MoviePilot 更接近上游自动化层，Jellyfin、Emby 和 Plex 是下游媒体服务器，Infuse 是最终消费客户端。MediaFlow 的位置应在“资源进入”和“下游可稳定消费”之间，并提供自己的统一管理与浏览入口。

### 3.2 核心优势与付费或采用驱动力

五个平台的商业模式不同，不能把所有核心优势都解释成付费权益。Infuse、Emby 和 Plex 具有明确的付费能力；MoviePilot 的价值更接近用户愿意投入部署与维护成本的采用驱动力；Jellyfin 则以免费、开源和自主控制降低采用阻力。

| 产品 | 核心优势 | 让用户付费或持续采用的主要原因 | 对结论的边界 |
| --- | --- | --- | --- |
| MoviePilot | 将订阅、下载监控、识别、整理、媒体服务器刷新和通知串成完整自动化，并通过大量插件覆盖常见 NAS 媒体生态 | 减少多工具之间的人工交接，以统一入口查看自动化状态，并按家庭环境扩展连接器 | 核心是自动化效率和生态适配，不应把其站点相关能力误认为 MediaFlow 必须提供的卖点 |
| Jellyfin | 免费开源、本地自托管、无高级许可证限制，强调隐私、数据控制和广泛客户端支持 | 避免订阅费用、追踪和必需云端账号，同时保留对服务器、媒体和客户端的自主权 | 这是采用驱动力而非付费权益；客户端体验仍需按具体平台分别验证 |
| Emby | 把媒体服务器、跨设备客户端、远程访问、家庭权限、直播电视与 DVR、离线和服务器管理组合成实用套件 | 用户为家庭日常使用所需的管理便利、客户端能力和服务器增强功能付费，而非只为单一功能付费 | 播放、转码、DVR 和专属客户端权益属于 Emby 边界，不应进入 MediaFlow Core |
| Plex | 广泛的设备覆盖、成熟的远程访问、跨设备发现与继续观看体验，以及面向家庭使用的高级服务器能力 | 用户为随时随地访问、较低的跨设备使用成本和成熟消费体验付费 | 云端账号、在线内容聚合、播放和转码不是 MediaFlow 的目标能力 |
| Infuse | Apple 原生体验、广泛格式直接播放、高质量音视频支持，以及对文件共享和多种媒体服务器的统一访问 | 用户为“连接来源后即可顺畅使用”的低折腾体验、视觉品质、跨设备同步和高级播放能力付费 | 播放器和 Apple 专属能力不照搬，但其信息组织与来源抽象可作为浏览体验标杆 |

这组对照说明，用户买单的不只是功能数量。长期价值通常来自三个方面：自动化节省时间，本地控制与可靠性建立信任，持续顺滑且有品质的界面降低每天重复操作的成本。

### 3.3 UI 与交互优势

以下判断基于各产品官方页面、文档和界面展示，目的是识别产品价值信号，不等同于对全部客户端完成了真实设备可用性测试。

| 产品 | 官方呈现的 UI 与交互优势 | 形成的用户价值 |
| --- | --- | --- |
| MoviePilot | 以统一仪表盘、功能入口、统计信息、任务状态和插件市场承载复杂自动化配置 | 管理者能在一个操作面中理解系统正在做什么、从哪里失败以及如何扩展，降低多工具切换成本 |
| Jellyfin | 使用熟悉的首页、媒体库、筛选排序和详情层级，并允许用户调整首页内容 | 媒体浏览的学习成本较低，界面和内容仍由自托管用户控制；优势是清晰与可配置，而不是未经验证的商业级一致性 |
| Emby | 同时提供面向家庭成员的媒体展示和响应式 Web 管理界面，把资源库、元数据、用户与权限配置可视化 | 管理者与消费用户可以在同一系统中完成各自任务，减少命令行配置和后台、前台割裂 |
| Plex | 在不同客户端维持相近的搜索、继续观看、Watchlist、推荐、浏览和集合导航 | 用户能快速恢复观看、寻找内容并在设备间迁移使用习惯，跨设备一致性本身构成付费体验的一部分 |
| Infuse | 以海报、背景图和清晰详情构成视觉完成度较高的媒体墙，通过筛选、收藏、集合和统一资源库隐藏来源差异 | 用户不必先理解文件共享或媒体服务器结构即可浏览内容，视觉品质和少步骤交互直接提升日常使用意愿 |

UI 漂亮和交互友好可以成为核心卖点，但必须落实为可观察价值：信息层级清楚、常用动作步骤少、状态和错误可理解、不同来源不增加浏览负担，以及在桌面和移动设备上保持稳定的操作习惯。主题、动画或大图本身不能替代这些能力。

### 3.4 对 MediaFlow 的启示

- 管理体验应主要借鉴 MoviePilot 的流程集中度和 Emby 的可视化管理，让自动化阶段、文件影响、失败原因和恢复入口始终可见。
- 浏览体验应主要借鉴 Infuse 的视觉组织和 Plex 的跨设备信息层级，同时保持 Jellyfin 所代表的本地控制、隐私和无必需云端账号。
- 管理者与家庭成员的首要任务不同。M1.4 应分别验证管理闭环和媒体浏览，不应让复杂系统配置侵入家庭成员的日常入口。
- MediaFlow 的价值主张不能只剩“又一个媒体墙”，也不能只提供后台自动化。更有辨识度的组合是安全、可解释的资源交接，加上达到日常消费品质的统一浏览入口。
- 界面可以隐藏连接器和来源差异，但不得隐藏文件操作、授权边界、主数据来源和任务真实状态。

## 4. 生命周期对照

### 4.1 资源进入

MoviePilot 支持搜索、订阅、手动下载、下载器监控和目录监控。订阅能够定期检查增量资源并触发下载，文件整理可以由下载器状态或目录变化触发。

Jellyfin、Emby 和 Plex 的标准入口是已经存在于授权媒体目录中的文件。它们要求先配置媒体库路径和内容类型，再扫描新增、删除或改变的内容。Infuse 的入口是文件共享或现有媒体服务器连接。

对 MediaFlow 的含义：

- “资源从哪里进入”必须是显式领域概念，不能隐藏在某个连接器配置中。
- MVP 可以先支持已授权目录扫描和人工触发，下载器自动接管留给后续里程碑确认。
- 站点搜索、Cookie 和私有索引不是资源进入方式。

### 4.2 文件发现与任务状态

MoviePilot 通过后台轮询下载器或实时目录监控发现文件。媒体服务器通过库扫描或文件系统监控发现变化。Infuse 会按连接模式缓存或按需读取媒体服务器内容，并周期性扫描更新。

对 MediaFlow 的含义：

- 扫描、监听和下载完成事件最终应进入同一种持久任务模型。
- 每次发现都需要显示来源、授权根目录、阶段进度、单文件错误和最终结果。
- 大目录扫描必须允许部分成功，不能因单个文件失败而丢失全部结果。

### 4.3 识别、命名与元数据

Jellyfin、Emby 和 Plex 都把目录结构、文件名和媒体库类型作为识别的重要输入。名称、年份、季度集号和 provider ID 能提高匹配准确度。Jellyfin 还支持从本地 NFO 读取和写出元数据，本地 NFO 的优先级高于远程 provider。

MoviePilot 在整理前完成媒体识别，并根据配置生成目标目录和文件名。Infuse 连接媒体服务器时直接使用服务器提供的元数据，不再自行从 TMDB 获取一套平行结果。

对 MediaFlow 的含义：

- 识别结果必须保存证据来源，而不只保存最终标题。
- parser、NFO、provider 和人工修改需要明确优先级。
- provider ID 是跨 MediaFlow、媒体服务器和播放器稳定交接的重要标识。
- 文件命名和 NFO 不是纯展示细节，而是下游兼容契约。

### 4.4 人工纠错

Plex 使用 Match 或 Fix Match 处理未匹配和误匹配项目；Emby 使用 Identify，并允许管理员直接编辑 provider ID 和元数据字段；Jellyfin 可以通过规范命名、provider ID、NFO 和元数据编辑改善识别。MoviePilot 提供整理历史、重新整理和失败分析入口。

这些产品大多从具体媒体项目或历史记录进入纠错。MediaFlow 可以进一步把低置信度、识别失败、命名冲突、文件操作失败和下游刷新失败聚合为统一收件箱。

课程、自制视频和其他非影视内容可能没有可用的外部 provider。统一收件箱可以提供“按通用视频人工整理”的候选选项：以原文件名、目录层级和媒体技术信息作为本地证据，由用户补充展示标题、分组、顺序和目标位置，并允许保留相对目录结构。该流程必须把字段来源标记为本地或人工输入，不得伪造外部匹配结果。

通用视频是否进入影视 MVP、采用独立资源类型还是只作为未匹配文件的临时处理方式，留给 M1.3 决定，本研究不提前扩大范围。

这是研究推断，不是对竞品缺失能力的完整断言。M1 后续需要用原型验证统一收件箱是否比按功能入口排错更高效。

### 4.5 整理与文件安全

MoviePilot 支持复制、移动、硬链接等整理方式和覆盖策略，并允许从历史记录重新整理。Jellyfin、Emby 和 Plex 的官方流程主要假设媒体已经按约定组织，它们负责扫描和匹配，不应作为 MediaFlow 文件操作安全设计的替代品。

对 MediaFlow 的含义：

- 整理必须先生成可追溯的 `OrganizationPlan`，再执行文件操作；可检查不等于每次都要求人工确认。
- 计划需要展示源路径、目标路径、操作类型、命名结果和冲突决策。
- 覆盖、删除和跨文件系统移动必须有更高确认强度。
- 执行必须具备持久操作日志（journal）、幂等恢复、审计和可解释的回滚结果。
- 自动整理与人工整理共用路径授权、冲突检查、持久操作日志、审计和恢复能力，避免维护两套行为不同的执行路径。
- 用户可以通过规则预先授权低风险、高置信度计划自动执行；只有低置信度、冲突、破坏性操作、越界路径或策略未覆盖的情况才中断并请求人工处理。

### 4.6 媒体服务器刷新

MoviePilot 可以在文件整理完成后通知媒体服务器刷新。Plex 明确区分 Scan 和 Refresh：Scan 用于发现新增、删除或移动的文件，Refresh 用于重新获取已有项目的元数据。Emby 和 Jellyfin 也分别提供库扫描、实时监控和元数据刷新能力。

对 MediaFlow 的含义：

- 只有用户显式配置并启用、具有授权凭据且与当前资源库建立映射的下游连接器才接收扫描或刷新请求；不得自动发现或广播给其他服务。
- 新文件整理完成后默认请求下游扫描，不应无差别刷新整个媒体库元数据。
- “已发出刷新请求”不等于“下游已经成功入库”。
- 连接器需要保存请求结果，并在能力允许时验证目标项目已经出现。
- 下游不可用不应回滚已经安全完成的本地整理，但必须产生可重试任务和明确告警。
- 未配置下游连接器时，本地整理仍可独立完成，不创建虚假的刷新成功记录。

### 4.7 浏览与外部播放

Infuse 连接 Plex、Emby 或 Jellyfin 时使用服务器提供的媒体库、元数据、版本、播放列表和播放状态。Direct Mode 强调按需读取和快速更新，Library Mode 强调多来源聚合与离线浏览。

对 MediaFlow 的含义：

- MediaFlow 可以提供媒体墙、详情、版本和任务状态，但不成为播放状态主数据。
- 播放动作应交给已配置的媒体服务器或外部播放器，并明确展示跳转目标。
- MediaFlow 的目录、provider ID 和 NFO 应提高下游一致性，而不是制造另一套不兼容目录。

## 5. 个性化与扩展能力分析

个性化与扩展能力横跨资源进入、识别、整理、建立媒体记录和消费，不能只作为界面主题或插件数量进行比较。本节关注哪些行为可以配置、配置属于谁，以及扩展如何进入主流程。

### 5.1 工作流个性化

MoviePilot 允许配置存储目录、媒体分类、电影与电视剧重命名格式、订阅模式、过滤规则和工作流，并通过目录监控、媒体服务器刷新等能力扩展自动化。Jellyfin、Emby 和 Plex 则主要在资源库级选择内容类型、扫描方式、元数据来源、语言和本地媒体优先级。

对 MediaFlow 的含义：

- 工作流个性化应覆盖来源、识别证据优先级、命名模板、目标目录、自动执行阈值、冲突策略和下游映射。
- 配置至少需要区分系统默认值与资源库覆盖值，并让最终生效值及其来源可见，避免相同输入因隐藏默认值产生无法解释的不同结果。
- 文件整理和下游通知属于管理行为，只能由具有对应权限的 NAS 管理者或媒体维护者配置；家庭成员的浏览偏好不得改变这些行为。
- 自动化规则需要版本或快照，使历史任务能够解释当时使用了什么配置；具体持久化方式留给 M1.6 架构设计。

### 5.2 内容与展示个性化

Emby 为本地用户提供独立的资源库访问、用户数据、语言和视图偏好，并允许管理员限制用户修改个人设置。Plex 支持按资源库、分级和标签控制访问，并提供手动、智能和自动合集。Infuse 可以选择纳入 Library 的目录，配置收藏、合集、排序、语言、本地元数据和本地图片优先级。

对 MediaFlow 的含义：

- 规范化元数据、资源库归属、文件位置和 NFO 属于共享主数据；收藏、固定入口、排序、筛选和展示语言属于用户或客户端偏好。
- 管理者的人工修正需要保存字段来源和锁定状态，防止后续刷新无声覆盖；家庭成员的展示偏好不应回写规范化元数据。
- 访问控制应独立于界面隐藏。用户看不到某个资源库或标签时，API 和外部跳转同样不能绕过授权。
- M1.1 只确认需要支持的个性化层级；具体页面布局、主题和控件交互留给 M1.4。

### 5.3 连接器与自动化扩展

MoviePilot 通过插件市场扩展目录监控、媒体服务器刷新、通知和其他自动化。Jellyfin 和 Emby 的插件可增加认证、元数据来源、通知目标和内容类型。Plex Webhook 可以把资源入库或播放等事件发送给外部服务。

对 MediaFlow 的含义：

- MVP 优先定义内置连接器的受控接口和能力声明，例如扫描、刷新、查询入库结果和发送通知，而不是先建设通用插件市场。
- 每个连接器都需要显式配置、授权范围、凭据、能力、健康状态和调用结果；工作流只能调用已启用且与当前资源库建立映射的连接器。
- 稳定 API、事件契约和 Webhook 可以作为首选的进程外扩展面，使外部自动化不必进入 Core，也不成为 Core 的运行时依赖。
- 在核心闭环和扩展契约稳定前，不开放可在 Core 进程内任意执行代码的第三方插件；是否需要沙箱插件机制留给后续里程碑基于真实扩展需求决定。

### 5.4 资源类型扩展

Plex 使用 Personal Media 或 Other Videos 处理家庭视频等非商业内容；Emby 插件的 Content Providers 可以增加图书和游戏等媒体种类；Jellyfin 通过 Bookshelf 等插件扩展图书元数据与组织；Infuse 允许家庭视频使用本地文件名、图片和 NFO/XML，而不强制依赖在线匹配。

对 MediaFlow 的含义：

- 统一模型应复用资源库、逻辑资源、物理文件、元数据来源、任务和审计等公共概念，但不能假设所有资源都有上映年份、季度集号或 TMDB ID。
- 新资源类型需要能够替换或组合自己的发现、识别、元数据、组织和展示策略，而不是在影视流程中不断增加类型分支；具体接口由 M1.6 验证。
- 电影和剧集仍是首阶段正式范围。课程、自制视频等通用视频只能在 M1.3 明确纳入后成为 MVP 承诺，否则保留为人工兜底候选能力。
- 资源类型扩展不等于一次性建设照片、图书和漫画功能。M7 仍应选择一种真实类型验证公共模型和扩展边界。

### 5.5 本地智能增强

MoviePilot 已提供智能助手、模型 provider、自定义模型地址、智能推荐和整理失败辅助重试等配置。MediaFlow 的既有产品定义也明确允许识别与元数据补全通过可选的本地或远程模型 provider 扩展。本地模型因此属于需要保留边界的扩展方向，但不应被等同于通用插件，也不代表当前 MVP 已承诺集成具体运行时。

本地智能增强可能覆盖多种能力，不能用单一“调用大模型”接口混合处理：

- 文本或结构化生成可以辅助理解非标准文件名、目录语义，规范化标题、分组和标签建议。
- Embedding 可以支持语义检索、相似资源发现和后续推荐，但其索引、更新和删除需要独立生命周期。
- 视觉、OCR、音频或多模态模型可以从封面、截图、课件和音轨提取证据，但资源消耗和隐私风险高于纯文本推理。
- 不同模型可能只支持部分能力，因此 provider 需要声明能力、模型版本、上下文限制、健康状态和预估资源需求，调用方不得仅凭模型名称推断行为。

对 MediaFlow 的含义：

- AI 输出只能作为带来源、模型版本、生成时间和置信信息的候选证据或建议；写入规范化元数据前仍需经过结构校验、优先级和人工确认策略。
- AI 不得直接移动、覆盖或删除文件，也不得绕过 `OrganizationPlan`、路径授权、冲突检查、持久操作日志和审计。
- parser、NFO、普通元数据 provider 和人工处理必须构成不依赖模型的基础路径。模型关闭、不可用、超时或输出无效时，任务应明确回退或进入收件箱，不能阻断扫描、整理和浏览。
- 长时间推理应进入持久任务体系，具备超时、取消、并发和资源预算；低资源 NAS 可以完全关闭智能能力或把推理指向另一台本地设备。
- 本地 provider 与远程 provider 必须区分数据边界。任何文件名、目录、图片、文本或媒体片段离开 NAS 前都需要显式配置和可见授权。
- M1.1 只确认能力分类和安全边界；M1.3 决定 MVP 是否只保留边界，M1.6 决定 provider 职责、任务数据流与部署方式，具体运行时和协议由后续实现验证。

研究阶段建议优先把本地模型视为“可选智能 provider”，而不是预先建设 AI 插件平台。只有实际接入多个稳定实现后，才能判断是否需要统一兼容协议、进程外插件或独立推理服务。

### 5.6 外部通知与 Bot 交互

MoviePilot 把应用内通知、按用户隔离的外部通知和远程消息交互组合在同一产品中，并针对企业微信回调、Telegram 轮询和 Slack Socket Mode 使用不同接入方式。飞书和 Slack 的官方能力也说明，简单群 Webhook、应用机器人、事件订阅和交互回调具有不同权限与网络要求，不能抽象成只有一个发送方法的“通知渠道”。

平台能力应至少拆成三类，由同一个适配器按实际支持情况声明：

- 通知出口负责向单个用户、群组或固定 Webhook 发送文本、卡片、附件和状态更新。
- 指令入口负责接收 Slash Command、菜单、显式文本命令或其他结构化请求，并保留平台、会话、发送者和消息标识。
- 交互回调负责处理卡片按钮、选择器、表单等已有消息上的操作，并关联原通知、业务对象和短期交互上下文。

只支持群 Webhook 的配置可以实现通知出口，但不能因此被视为支持指令。需要双向交互的平台通常还要求应用凭据、事件订阅、回调签名、用户身份和额外权限，应该采用独立配置与能力检查。

对 MediaFlow 的含义：

- 领域流程先生成与平台无关的通知意图，至少包含事件类型、严重程度、摘要、目标对象、接收范围、敏感级别和 MediaFlow 深链接，再由渠道适配器渲染为平台支持的消息格式。
- 通知策略需要按用户、角色、资源库、事件类型和严重程度选择渠道与接收者，并支持聚合、静默时段、限流和失败降级，避免同一故障在多个渠道形成通知风暴。
- 每次投递需要记录目标配置、平台消息 ID、尝试次数、最终状态和错误，但不得在通知、日志或诊断中泄露完整路径、令牌、Cookie、密码或连接器密钥。
- 外部平台用户必须显式绑定到 MediaFlow 用户或受限服务身份。未知、未绑定或已停用的外部身份直接拒绝，不能自动回退为管理员权限。
- 入站事件必须验证平台签名、时间戳或加密信封，并按平台事件 ID 或等价键去重。平台重试不得创建重复任务或重复执行操作。
- 回调层应尽快确认“已接收”，再把有效指令写入持久任务；接收成功、任务创建成功和业务执行成功是三个不同状态，最终结果异步回复操作人。
- 公网 Webhook、长连接、Socket Mode 和轮询是不同传输方式。连接器应按平台能力选择，不要求所有本地部署都暴露 NAS 公网入口。

首阶段 Bot 指令采用分级策略：

- 查询类指令可以查看当前用户有权访问的任务状态、连接健康、待处理数量和资源信息。
- 低风险、可幂等指令可以创建重试、重新扫描授权资源库等任务，但仍需经过参数校验、权限检查、去重和审计；具体命令清单由 M1.3 确认。
- 文件移动、覆盖、删除、跨授权根目录操作以及连接器、用户和系统配置修改，不得仅凭 Bot 消息直接执行。Bot 只能创建待确认项并返回一次性 Web 深链接，由用户在正式界面查看影响后确认。
- 自然语言或本地模型可以把消息转换为结构化指令草案，但不得直接调用领域执行器；草案仍需通过命令 schema、身份权限、风险分级和确认策略。
- 交互回复默认只发送给操作人。群内广播执行结果必须由通知策略显式允许，避免泄露个人任务、目录或资源信息。

当前路线图基线中，M3 明确不实现通知渠道，M4 只承诺应用内通知和通用出站 Webhook。因此飞书、企业微信、Slack 等专用适配器以及入站 Bot 都是待确认候选能力，不是当前里程碑承诺；如果 M1.3 决定提前纳入，必须同步调整路线图并重新确认范围。

M1.1 只确认渠道能力、身份和风险边界。M1.3 决定首批出站渠道、Bot 指令清单和里程碑归属；M1.4 设计通知卡片与确认跳转；M1.6 定义通知意图、身份绑定、事件去重、任务关联和审计模型。

### 5.7 分层原则

竞品研究支持将个性化与扩展划分为四层：

| 层级 | 主要内容 | 主要控制者 | 边界 |
| --- | --- | --- | --- |
| 系统与自动化策略 | 默认识别、命名、授权根目录、执行阈值和连接器 | NAS 管理者 | 可影响文件和外部系统，必须审计 |
| 资源库与资源覆盖 | 内容类型、元数据来源、字段锁定、合集和目标路径 | 管理者或媒体维护者 | 覆盖范围和优先级必须可见 |
| 用户与客户端偏好 | 可见资源、收藏、排序、筛选、语言和展示方式 | 家庭成员 | 不得改变共享主数据或文件系统 |
| 扩展接口 | 连接器、API、事件、Webhook、通知与 Bot、智能 provider 和未来类型策略 | 管理者与扩展开发者 | 必须经过能力声明和显式授权 |

这是对 MediaFlow 产品边界的研究推断，不代表已经确认具体配置模型、权限矩阵或插件架构。这些内容分别交给 M1.2、M1.3 和 M1.6 决定。

## 6. 值得借鉴的模式

### 6.1 自动化建立在可见阶段上

将下载完成、发现、识别、整理和刷新拆成阶段，既能自动运行，也能让用户知道失败发生在哪里。

### 6.2 规范化输出作为产品能力

文件名、目录、provider ID、NFO 和版本标签共同形成下游契约。MediaFlow 应预演并验证这些输出，而不是把它们当作用户自行维护的前置条件。

### 6.3 人工纠错回写识别依据

人工选择正确媒体后，应保存 provider ID、匹配证据和字段来源，使重新扫描和重新整理能够复用决定。

### 6.4 扫描与刷新保持不同语义

新增文件优先触发扫描，元数据问题才触发刷新。区分操作目的能减少大媒体库中的无效工作和意外覆盖。

### 6.5 消费端服从明确的主数据来源

Infuse 使用媒体服务器元数据的方式说明，消费端不需要重复生成一套元数据。MediaFlow 也应明确何时以本地 NFO、远程 provider、人工修正或媒体服务器状态为准。

## 7. 明确排除的模式

- 不把私有站点搜索、Cookie 管理和资源索引聚合纳入 Core。
- 不复制 Jellyfin、Emby、Plex 或 Infuse 的播放、转码和播放进度能力。
- 不在核心闭环稳定前依赖庞大插件市场解决基本流程。
- 不把全库元数据刷新作为新增文件后的默认动作。
- 不允许后台自动化绕过预演、路径授权、冲突处理、持久操作日志和审计。
- 不让用户展示偏好改变共享元数据、文件位置或下游整理结果。
- 不在核心闭环和扩展契约稳定前建设通用插件市场或开放任意进程内代码扩展。
- 不把外部平台用户 ID、群成员身份或共享 API Token 直接等同于 MediaFlow 管理员身份。
- 不把 Bot 回调已接收显示为任务创建或业务执行成功，也不允许平台重试导致重复执行。
- 不允许 Bot 指令绕过正式界面对文件与系统配置高风险操作的预演和确认。
- 不把“请求已发送”显示为“媒体已成功入库”。

## 8. MediaFlow 产品机会

基于官方资料可以提出一个待后续验证的差异化方向：MediaFlow 成为现有文件来源与媒体服务器之间可解释、可预演、可恢复的交接层。

候选闭环为：

```text
授权来源产生文件
  -> 持久任务发现并记录来源
  -> 本地证据与 provider 联合识别
  -> 置信度判断
  -> 自动通过或进入统一收件箱
  -> 生成可检查的整理计划
  -> 安全执行并记录持久操作日志
  -> 请求媒体服务器扫描
  -> 验证或提示下游入库结果
  -> 在 MediaFlow 浏览并跳转外部播放
```

该方向需要在 M1 的用户、范围和原型阶段继续验证，当前不构成已承诺的 MVP 功能清单。

## 9. 后续待决问题

以下问题交给 M1.2、M1.3、M1.4 和 M1.6，不在竞品研究中提前决定：

1. MVP 的首要用户是 NAS 管理者、日常媒体维护者，还是两者合一。
2. MVP 首个资源入口是现有资源库扫描、独立收件目录，还是人工添加文件或目录。
3. 自动识别达到什么条件可以跳过人工确认。
4. NFO 是默认写入、按资源库配置，还是仅复用已有文件。
5. 首个媒体服务器连接器选择 Jellyfin，还是先定义兼容 Jellyfin、Emby 和 Plex 的最小公共能力。
6. 闭环完成以本地整理成功、刷新请求成功，还是验证下游可见为准。
7. M1 原型是否需要包含媒体墙和外部播放跳转，还是只验证管理闭环。
8. 课程、自制视频等通用视频是否进入 MVP，以及采用独立资源类型还是未匹配文件的人工整理方式。
9. 系统、资源库和用户配置分别由谁管理，覆盖顺序和最终生效值如何展示。
10. MVP 首批连接器只提供内置适配，还是同时承诺稳定 API、事件或 Webhook 扩展面。
11. 哪些用户偏好需要跨客户端同步，哪些只属于单个客户端的本地展示状态。
12. 首个本地智能增强场景是非标准文件名识别、通用视频分类、元数据补全，还是语义检索，以及如何衡量它优于基础路径。
13. 本地推理由 MediaFlow 部署包携带，还是连接用户独立部署在 NAS 或局域网设备上的运行时。
14. 是否允许可选远程模型 provider，以及哪些字段和媒体证据可以在显式授权后离开 NAS。
15. 首批外部通知是否维持 M4 的通用出站 Webhook 基线，以及飞书、企业微信或 Slack 等专用适配器应进入哪个后续里程碑。
16. 哪些通知默认发送给操作人、管理员或家庭成员，以及资源标题、目录和错误详情分别允许进入哪些渠道。
17. 首批 Bot 查询与低风险指令包含哪些操作，外部身份如何与 MediaFlow 用户完成绑定、撤销和设备丢失后的恢复。
18. 本地部署接收入站消息时优先使用公网回调、平台长连接、Socket Mode、轮询还是用户自建代理。
19. MediaFlow 首要价值承诺是自动化节省时间、安全可控，还是高品质统一浏览，以及首次使用时应优先证明哪一项。
20. M1.4 对管理界面和浏览界面分别采用哪些竞品作为主要基准，以及如何把“漂亮、友好”转化为可验收的任务与状态标准。
21. 管理者和家庭成员是否共享同一个默认首页，还是根据角色提供不同的首屏信息与操作入口。

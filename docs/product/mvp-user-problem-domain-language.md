## 1. 文档目的

本文细化 [MediaFlow 产品定义](product-definition.md) 中与 MVP 用户、问题和语言有关的基线，并承接 [MVP 竞品与现有工作流研究](mvp-competitor-workflow-research.md) 和 [路线图 M1](../plans/roadmap.md) 的结论，供后续范围、需求、交互和架构工作共同引用。它回答以下问题：

1. 谁首先使用和验证 MediaFlow。
2. 现有工具链中的主要问题是什么。
3. 怎样判断产品闭环和 AI Coding 项目验证成功。
4. 后续文档应使用哪些词，以及哪些相近概念必须区分。

本文不决定 MVP 的完整功能清单、页面结构、API、数据库模型、权限矩阵或连接器实现。这些事项由后续 M1 节点分别确认。

## 2. 用户

### 2.1 首要产品用户

MVP 的首要产品用户是有一定 NAS 经验的家庭管理维护者。此人已经使用下载器、媒体目录、媒体服务器和播放器，能够理解路径、服务连接和基础系统状态，但不应被要求通过脚本或数据库完成日常媒体管理。

MVP 阶段将以下职责视为同一个人承担：

- 配置专用收件目录、资源库、整理规则、元数据来源，以及可选的 Jellyfin 独立连接和其他 MVP 内置能力。
- 处理低置信度识别、通用视频分组歧义、文件冲突和本地失败任务等日常异常。
- 检查自动化为什么做出某个决定，并在必要时修正或重试。

这只是 MVP 的用户假设，不等于未来权限模型必须把管理者和维护者永久合并。

### 2.2 MVP 外部消费方与后续用户

MVP 只为管理员提供 MediaFlow 账号和界面。家庭成员直接使用 Jellyfin 浏览和播放媒体，不进入 MVP 的 MediaFlow 用户、权限或界面验收范围。

家庭成员仍是后续产品用户。M4 再增加家庭成员角色和面向消费的 MediaFlow 浏览入口；这项后续方向不能反向扩大 M3/MVP 的完成条件。

### 2.3 首位项目验证者

当前首位项目验证者是具备计算机知识的程序员，与首要产品用户存在重叠。这有利于验证早期技术和协作流程，但“会编程”不是 MediaFlow 面向未来用户的必要条件，也不能成为界面难懂或流程依赖手工技术操作的理由。

## 3. 当前处境

目标用户通常不是从空白环境开始，而是已经拥有以下工具和内容：

- 下载器或其他经过授权的文件来源。
- 按目录保存的现有媒体文件。
- Jellyfin、Emby、Plex 等媒体服务器。
- Infuse、媒体服务器客户端或其他播放器。

这些工具各自能够完成部分工作，但文件来源、识别依据、整理结果、媒体服务器状态和浏览入口分散在不同系统中。用户需要自行判断本地资源当前处在哪个阶段、哪个系统是事实来源，以及失败后应该从哪里恢复。

## 4. 核心问题与产品价值

MediaFlow 长期需要处理两个相关问题：

1. 管理者缺少一个安全、可解释、可预演、可恢复的资源整理过程，难以确认文件为什么被这样识别和整理、实际改动了什么、本地结果是否完整。
2. 家庭成员面对分散的目录和服务入口，缺少统一且有品质的媒体浏览体验。

MVP 先验证第一个问题：管理员通过 MediaFlow 完成从专用收件目录到安全文件操作、受控 NFO 和本地结果可查的规则约束自动整理闭环，家庭成员继续直接使用 Jellyfin。第二个问题保留为 M4 及后续方向，不作为 M3/MVP 的 MediaFlow 内验收项。

自动化是减少重复操作的手段，不是独立的产品目标。MediaFlow 的价值是让资源从来源到本地整理结果的过程更可靠、更容易理解；媒体服务器如何观察目标目录由用户在对应服务中独立配置。

## 5. 成功标准

### 5.1 产品成功标准

MVP 按管理员能否完成闭环判断，不以功能数量代替结果。一个代表性资源至少满足以下条件，才算完成产品闭环：

1. MediaFlow 从显式配置的专用收件目录发现文件，并保存可追踪的处理任务。
2. 系统完成确定性识别，或把低置信度结果隔离为可修正的待确认记录。
3. 命中授权规则的低风险计划完成本地整理和受控 NFO 写入；异常计划可靠暂停且不越过文件安全边界。
4. MediaFlow 建立可追踪的媒体记录，并明确展示实际文件变化、NFO 结果和可恢复动作。
5. Jellyfin 未配置或不可用不会改变上述结果；管理员只在概览或设置查看其独立健康状态，并可打开已配置的 Jellyfin 首页。

异常路径同样属于成功标准：管理者能够知道失败发生在哪个阶段、已经产生哪些结果、哪些内容没有执行，并能够通过确认、修正、重试或回滚进入可理解的后续状态。任何后台自动化都不能绕过授权目录、预演、冲突处理和审计边界。

家庭成员直接使用 Jellyfin 的体验不属于 MVP 的 MediaFlow 内验收；MVP 不提供家庭成员账号、媒体墙或权限角色。

M1.2 不提前规定自动识别率、人工介入率、处理耗时或失败率等数字。具体指标只有在 M1.3 定义可验收场景、M1.6 定义质量与性能边界，并有真实实现可测量后才具有意义。

### 5.2 AI Coding 项目验证标准

本项目同时用于验证完整、可审查、可恢复的 AI Coding 人机协作流程，并帮助项目发起者学习相关技术。跨会话恢复是硬标准：一个新的 AI 对话只读取仓库，不依赖旧对话记录，就应能够说明：

- 当前处于哪个里程碑、Schema 和工作节点。
- 哪些决定已经获得人工确认，依据是什么。
- 已经产生哪些权威文档、实现产物和 Git 记录。
- 第一项未完成任务是什么，当前恢复点在哪里。
- 下一步需要谁使用哪个产物，以及下一个人工确认点是什么。

恢复依据由仓库规则、权威文档、实际工作区和 Git 记录共同构成。过程记录帮助人理解执行过程，但不能替代权威产物。

AI Coding 流程验证成功不代表产品需求、架构或实现自动通过验收；每项内容仍需要对应检查和人工确认。

## 6. 统一领域语言

### 6.1 对象与位置

| 术语 | 含义 | 使用边界 |
| --- | --- | --- |
| 资源 | 尚未明确具体类型时的泛称 | 已知对象类型后优先使用文件、媒体项目或媒体版本；不单独用于成功状态 |
| 来源 | 文件进入 MediaFlow 管理流程的入口 | 不等同于元数据来源；可以是授权目录、下载完成事件或后续确认的其他入口 |
| 目录 | NAS 文件系统中的实际目录 | 路径是否可读写必须受授权根目录约束 |
| 文件 | NAS 文件系统中的实际文件 | 与用户浏览的逻辑媒体项目分开描述 |
| 媒体项目 | 用户浏览和理解的逻辑内容 | 可以表示电影、剧集等内容，不直接等同于某个文件 |
| 媒体版本 | 同一媒体项目的一种具体版本 | 可以关联 1080p、4K、导演剪辑版等一个或多个实际文件 |
| MediaFlow 资源库 | MediaFlow 管理的一组授权目录、规则和媒体项目 | 具体数据模型与目录数量由 M1.6 决定 |
| 外部媒体服务器 | Jellyfin、Emby、Plex 等独立管理媒体目录的服务 | MVP 不建立其媒体库与 MediaFlow 资源库的映射；服务是否监控整理目标目录由用户在外部系统配置 |
| 收件箱 | 汇总需要人工处理项目的工作入口 | 不是文件系统目录；可包含识别失败、低置信度、冲突和失败结果 |

### 6.2 处理动作

| 术语 | 含义 |
| --- | --- |
| 发现 | 注意到一个可能需要处理的新文件或变化 |
| 扫描 | 枚举目录并对账文件的新增、变化和缺失 |
| 识别 | 根据本地与外部依据判断文件对应的媒体身份 |
| 补充元数据 | 为已识别或人工建立的媒体项目获取、合并或填写展示信息 |
| 人工确认 | 由用户确认、修正或补充系统无法可靠决定的内容 |
| 生成整理计划 | 计算拟执行的目标位置、文件操作和相关输出，但尚未修改文件 |
| 预演 | 向用户展示整理计划、影响和冲突，供检查或授权 |
| 整理 | 按已经确认或规则授权的计划执行文件操作并记录结果 |
| 建立媒体记录 | 在 MediaFlow 中建立或更新媒体项目、媒体版本、文件和元数据之间的关系 |
| 名称格式化 | 按显式格式和确定性依据规范文件或目录名称，不等同于识别媒体身份 |
| 相似内容聚合 | 按来源目录、规范化名称、连续编号或显式规则把相关通用视频归为一组；模糊相似必须人工确认 |
| 文件夹归类 | 按已确认规则计算并展示目标文件夹层级，仍受授权根目录和冲突检查约束 |
| 刷新元数据 | 请求重新获取或计算已有媒体项目的信息；不作为新增文件后的默认同义操作 |
| 浏览 | 在 MediaFlow 中查看媒体列表、筛选结果和详情 |
| 打开外部服务 | 从概览或设置打开已配置外部服务的首页；MVP 不把它与具体媒体项目关联 |

不再使用“编目”描述“建立媒体记录”。“入库”也不作为独立动作，因为它无法说明本地文件和 MediaFlow 记录中究竟发生了什么。

### 6.3 任务与状态

| 术语 | 含义 |
| --- | --- |
| 任务 | 可持久化、可观察、可取消或重试的处理过程 |
| 阶段 | 任务内部的一个明确步骤，例如扫描、识别、计划、文件操作或 NFO 写入 |
| 待确认 | 系统暂停，等待用户补充或批准后续动作 |
| 冲突 | 当前计划不能按规则安全执行，需要选择或修正 |
| 部分成功 | 任务只完成部分目标，必须同时列出成功项、失败项和可恢复动作 |
| 失败 | 当前任务无法继续，必须保留失败阶段、原因和已产生结果 |

描述结果时必须指出对象和阶段，例如“文件操作成功”“NFO 写入失败”“本地整理成功”和“已建立媒体记录”。不得用“入库成功”覆盖多个尚未完成或无法区分的状态。

这些词描述产品语义，不提前规定数据库枚举或 API 字段；正式状态模型由 M1.6 和对应实现 change 定义。

### 6.4 依据、规则与外部系统

| 术语 | 含义 | 使用边界 |
| --- | --- | --- |
| 识别依据 | 用于判断媒体身份的信息 | 可以来自文件名、目录层级、NFO、provider ID、媒体技术信息或人工输入 |
| 元数据来源 | 某个元数据字段来自哪里 | 应区分本地文件、NFO、外部元数据提供方和人工输入 |
| 置信度 | 系统对识别结果可靠程度的表达 | 不等于文件操作权限；高置信度仍必须满足授权规则 |
| 规则 | 决定如何识别、整理或处理异常的可配置条件 | 最终生效规则及其来源需要可见，具体覆盖模型由 M1.6 决定 |
| 外部系统 | MediaFlow 之外被连接的服务 | 包括下载器、元数据提供方、媒体服务器、通知渠道和可选模型运行时 |
| 连接器 | MediaFlow 与一类外部系统通信的适配边界 | 每种连接器只能使用已确认能力；Jellyfin 在 MVP 中仅用于连接测试、健康状态和全局首页入口 |

## 7. 词汇在闭环中的关系

```text
来源产生文件
  -> 发现或扫描
  -> 使用识别依据进行识别
  -> 人工确认或生成整理计划
  -> 预演并整理
  -> 建立媒体记录和媒体版本关系
  -> 在 MediaFlow 浏览
```

Jellyfin 等外部媒体服务器可以由用户独立配置为观察整理目标目录，但不进入上述 MediaFlow 任务链。

该流程用于解释词汇关系，不是 M1.3 的完整功能承诺，也不规定各阶段必须采用同步还是异步实现。

## 8. 后续阶段边界

### 8.1 交给 M1.3

- MVP 首个资源入口和正式支持的资源类型。
- 自动识别阈值、人工确认条件和 NFO 策略。
- 元数据、Jellyfin、通知和 Bot 的 MVP 边界。
- 通用视频、本地模型和扩展能力的阶段边界。
- 可验收需求、非目标和完整场景。

### 8.2 交给 M1.4

- 管理员的信息架构和默认首页。
- 专用收件目录、收件箱、整理计划、任务状态和失败恢复的具体交互。
- 管理员媒体列表、详情，以及概览或设置中的 Jellyfin 独立健康状态和全局首页入口。
- Loading、Empty、Error、Offline、Conflict 和 Partial Success 等界面状态。

### 8.3 交给 M1.6

- 媒体项目、媒体版本、文件、资源库、任务和连接器的正式领域模型。
- 单管理员身份、未来角色边界、配置覆盖和最终生效值模型。
- 文件安全、任务恢复、审计、扩展接口和本地模型架构。
- API、事件和实现模块边界。

M1.2 不生成实现规格，也不初始化 Core、Web、数据库或客户端。M2 及后续实现必须根据已经确认的范围和架构重新定义可实现、可验证的具体能力。
